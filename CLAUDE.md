## Key Conventions

- **Two devices, one cable, almost no shared state**. iPad is a MIDI controller (USB-MIDI only — no Bonjour/Wi-Fi). It owns its glide/vibrato params, calibration, and the MPE emission. Mac is the **sarangi model** (`SarangiKit`) + tanpura/sitar + FX layer in front of a hosted Audio Unit (**SWAM Violin** `Svl3`, run dry — the sarangi base). It owns the sarangi model state, master FX, presets, and hosted-AU selection. The two communicate only over the USB cable. **Do not introduce shared params** beyond the one documented exception below — if a feature wants to live on one side, all its state lives on that side.
- **The one exception: Pitch/Chord Pad sync (Mac → iPad over SysEx).** StarpadMac edits; Starpad performs. The Mac pushes a `SyncedScaleState` (the `PitchScale` **plus `tonicMidi`, `marginPixels`, and the active `layout`** — `PadLayout.pitchPad`/`.chordPad`/`.stringPad`, which surface the iPad shows; `marginPixels` is the **active** layout's margin/sharpness, since each pad owns its own slider) to the iPad as a MIDI **SysEx** blob on the same USB cable: `PitchScaleSysEx.encode` = `F0 7D 01 base64(compact-binary) F7` (kept small so it clears the iOS USB-MIDI SysEx bridge; blob `version` is now `3`). The iPad's `ScaleSyncReceiver` receives it via an **input port connected to every source** (USB-incoming MIDI arrives as a *source* on the iPad — a virtual destination does NOT catch it; this was the bug) plus a virtual destination as backup, reassembles SysEx across packets/callbacks, and calls `PitchPadEngine.applySyncedState` (panics on scale **or layout** change, swaps scale/tonic/margin/layout). It persists to `SyncedScaleStore` (UserDefaults) for offline relaunch. One-way; the iPad has **no** scale editor, its tonic readout is read-only, and it can't pick its own layout. Push is driven from `AppController` via Combine: `Publishers.MergeMany` of `pitchPad.$scale` / `$tonicMidi` / `$marginPixels` / `chordPad.$marginPixels` / `stringPad.$marginPixels` / `$stringArrangement` / `$ipadLayout` / `midi.$destinationCount`, debounced, → `MIDIEngine.sendSysEx(_:toDestinationsMatching: "Starpad")` (falls back to all destinations if the name matches none — the bridged iPad endpoint shows up as "iPad", not "Starpad Scale"). **Second SysEx message:** the String Pad's note layout is its own state (not derivable from the scale), so while `.stringPad` is active the Mac ALSO pushes `StringArrangementSysEx.encode` = `F0 7D 02 base64(…) F7` (subtype `0x02`); `ScaleSyncReceiver` decodes it into its `@Published stringArrangement` (persisted via `StringArrangementSyncStore`). These two messages are the **only** SysEx and the **only** cross-device state in the app.
- **StarpadCore package** (`Packages/StarpadCore/`) — cross-platform building blocks: `Scale`, `MIDIEngine`, `MIDIInput`, `Config`, `MotionSource` protocol, `CalibrationData`. Also includes the **shared Pitch Pad** (`PitchPadEngine` — per-touch MPE + iPad tilt loop; `PitchPadGeometry.swift` — Voronoi solver/caches, soft-margin `pitchAt`, octave ghosts, OKLCH colors, `CellFillsView`; `ChordPadGeometry.swift` — the shared **Chord Pad** geometry (hex lattice, `chordCells` diatonic-chord pitch model, `chordPitchAt` soft-margin blend, hex polygons; reuses `pitchColor`/`CellFillsView`); `ScaleStore` — JSON scale persistence; `PitchPoint`/`PitchScale`), `NoteManager` (tilt/mapping host), and `AudioEngine` + `SarangiProcessorAU` (Mac-only audio — the in-process AUv3 effect that renders the sarangi model inline in the SWAM signal path). `PitchPadEngine` has two inits: `init(audio:)` (Mac, in-process delivery to `AudioEngine`) and `init(midi:)` (iPad, real USB-MPE through the shared `MIDIEngine`). Both iOS and macOS targets import the same package; each only uses the parts that apply. **Anything used outside the package must be `public`.**
- **SarangiKit package** (`Packages/SarangiKit/`) — the **played sarangi voice**, vendored wholesale from the standalone `~/Desktop/sarangi` model (pure DSP + model, no CoreAudio; re-sync by recopying `Sources/SarangiKit/{DSP,Model}` + `Resources/*.json`). `SarangiEngine.renderSample(input, amp) -> (L,R)` is the full block chain (dry SWAM in → complete sarangi out: bank/jawari/body, then the per-voice FX rack). Model types: `SarangiParams` (23 params via `ParamSpec`, `structural` flag), `LiveScalars`, `EQBand`/`VoiceFXParams`/`FXRack` (the per-voice FX rack), `RagaTuning`/`Raga`/`StringSpec` (editable tarab), `InstrumentState` (the persisted document — carries `fx`), `Presets` (pair1/pair2 + body FIR resources), `SignalAmpFollower`. `StarpadCore.AudioEngine` imports it (the `SarangiProcessorAU` effect, spliced into the graph after the SWAM AUs, runs `renderSample` on the pulled SWAM audio inline). See [docs/sarangi.md](docs/sarangi.md). **`StarpadDSP` no longer owns any sym/sarangi DSP** — it was all deleted (`OfflineEngine`, `SarangiResonator`, `SarangiSymVoice`, `SarangiExciter`, `SymBodyFilter`, `SchroederRoom`, `DSPParams`, `DSPConfig`, the `sym-render` tool).
- **StarpadDSP package** (`Packages/StarpadDSP/`) owns the **tanpura drone + sitar** (only — the sarangi moved to `SarangiKit`): the **tanpura** (`TanpuraModel`/`TanpuraString`/`TanpuraParams`): 4 harmonic-resolved strings where every harmonic (up to 64) gets its own bloom envelope (gain/peak-time/decay laws + per-harmonic trim arrays) plus a per-string **half-integer sub-bank** (`subLevelDB`, partials at `(k+0.5)·f0` — the jawari period-2 signature, loud in the reference), matched to `tanpura.mp3` by `tools/tanpura_match.py` + `tools/tanpura_iterate.py` through the package's **`tanpura-render` executable** (offline, ~50× real time; build with `swift build -c release --package-path Packages/StarpadDSP`). The primary metric is `specres` (per-cell |ΔdB|, absolute 90 Hz–16 kHz grids) judged against the two-seed stochastic floor; `tanpura_match.py report <wav> --floor <wav2> --diff-audio` is the acceptance-bar artifact. The match generalizes across **8 reference recordings** — `tanpura.mp3` (densely strummed, has the per-harmonic matrices) plus `tanpura1–7.wav` (varied tonics/density; calibrated by `calibrate-aux` into `auditions/tanpura/refs/<name>/`, scored by an aux minibatch with per-reference tuning and shared timbre). The isolated-pluck "wah-wah" (the summed envelope pumps) is fixed by `jivaConserve` (power-conserving jiva) + `jivaRateSpread` (tightens the per-harmonic rate scatter) under the `modspec` loss term (penalizes envelope-modulation energy above the reference's tight ~2 Hz pulse). Matched winners are baked into the `TanpuraParams` Swift defaults by `tools/tanpura_bake_defaults.py --bump` (peak-normalizes `masterGain`, bumps `matchedVersion` so persisted UserDefaults don't shadow the new bake). **Before trusting any matching run, verify the pluck schedule with `tanpura_match.py schedule-check`** — the loss conditions on it. `StarpadCore.AudioEngine` imports the package — the tanpura on its own source node behind `tanpuraLock`, the sitar likewise behind `sitarLock` (the **sarangi** runs the full model — incl. its per-voice FX rack (Violin/Sym/Global) — inline in the `SarangiProcessorAU` effect (spliced after the SWAM AUs) from `SarangiKit`, going `symGain → mainMixerNode` direct, BYPASSING the master FX; only tanpura/sitar use `preReverbMixer`→master reverb); don't duplicate DSP logic in any consumer. See [docs/tanpura.md](docs/tanpura.md) and [docs/sitar.md](docs/sitar.md).
- **iPad playing surface: the Pitch Pad** (`PitchPadEngine` + `PitchPadView_iOS.swift`), shared with the Mac Pitch Pad tab. It replaced the piano keyboard. Touch position → JI ratio (shared `pitchAt` soft-Voronoi in `PitchPadGeometry.swift`) → `PitchPadEngine` pins a MIDI note and bends; a 60 Hz tilt loop (started in the iPad `init(midi:)`) overlays vibrato/aftertouch/CC. The pad is multitouch-polyphonic (one MPE channel per finger) and play-only on iPad (editing via the list-editor sheet); the Mac tab has the full editing toolkit. The iPad does not synthesize; it only emits MIDI.
- **`NoteManager` (iPad) is now the tilt/mapping host, not the playing orchestrator.** It still runs (its 60 Hz loop samples tilt into `currentTilt` and owns the `DimensionMapping` matrix that `MappingMatrixPanel` edits), and `PitchPadEngine.expression` is a weak ref to it for `cachedParamValue(...)` / `activeCCs`. Its keyboard/glide/voice (`pitchChannels`) MIDI paths stay idle because nothing calls its `touchBegan`. The old keyboard/glide-queue/snap pipeline lives on but is unused on the playing path.
- **Mac orchestration: `AppController`**. Owns the editable Mac state (the `SarangiStore` for the sarangi model, tanpura/sitar params, master FX, current preset). On preset switch or slider change, it pushes directly to `AudioEngine`. `NoteManager` is **not used** on the Mac for real-iPad MIDI input — but the **Simulator tab** (`StarpadMac/IPadSimulator.swift`) owns its own `NoteManager` + `MockMotionSource` so the Mac can play notes from a mouse + tilt sliders, for autonomous sound-design iteration. The simulator's `MIDIEngine` uses `publishToCoreMIDI: false` and an in-process `onLocalEvent` callback to deliver MIDI directly into `AudioEngine.sendHostedMIDI` + `AppController.handleSimulatorCC`, so it never feeds `MIDIInput` and coexists with a plugged-in iPad.
- **Chord Pad tab (Mac-only).** `AppController` holds a **second** `PitchPadEngine` (`chordPad`, beside `pitchPad`, also `init(audio:)`/in-process) as the MPE emitter for the hex-grid chord surface (`StarpadMac/Views/ChordPadView.swift`). The grid (`ChordPadGeometry.swift`) maps a diatonic scale → per-cell `2^(semis/12)` ratios and feeds the engine's ratio API; it **reads** the scale + tonic from `pitchPad` (read-only — `chordPad.tonicMidi` is kept in step via a Combine sink in `start()`), adds **no** cross-device state, and is not part of scale sync. The two Mac engines round-robin the same 15 MPE channels, so play one pad at a time. Common scales are **shared**, not Chord-Pad-local: `ScalePreset` (modes, major/minor, pentatonics, in `ChordPadGeometry.swift`) loads into the one `pitchPad.scale` via `PitchPadEngine.loadPreset`, reachable from both the Chord Pad toolbar and the Pitch Pad's Scale → Scales submenu. The Chord Pad **also runs on the iPad** (`ChordPadViewIOS` in `PitchPadView_iOS.swift`): selecting the Mac's **Pitch Pad** or **Chord Pad** tab sets `AppController.ipadLayout` (via `MacMainWindow.selectTab`, covering both the segmented picker and the ⌘-number shortcuts), which rides the synced state, and the iPad swaps surfaces on `pad.layout`. See [docs/chord-pad.md](docs/chord-pad.md).
- **String Pad tab (Mac-only, ⌘8).** A box-plot / abacus surface (`StarpadMac/Views/StringPadView.swift`). `AppController` holds a **third** `PitchPadEngine` (`stringPad`, beside `pitchPad`/`chordPad`, `init(audio:)`/in-process) as the MPE emitter, plus `@Published var stringArrangement` (a `StringArrangement` = `notes:[StringNote]` + `stringCount` + `ghostStringsPerSide`). **Strings are explicit, evenly-spaced indexed columns** — a `StringNote` has `stringIndex` (NOT a free `x`), `degreeIndex`, `octave`, `centerY`, `height`. A **note** = name + pitch + `centerY` + `height`, drawn as a **single hexagon** (rectangular middle + a fixed-length tip top/bottom, `stringTipLength`) with **constant pitch throughout** (tips included). A note's pitch is a **scale degree** of `pitchPad.scale` (+ octave), looked up live (`scaleDegrees(from:)`/`noteRatio`), and its **name is sargam** derived from the pitch (`noteName`/`sargamName`: S r R g G m M P d D n N = degrees 1, 2♭, 2, 3♭, 3, 4, 4♯, 5, 6♭, 6, 7♭, 7 of the default scale; `'`/`,` = octave up/down). **Strings repeat across octaves**: `stringColumns()` lays out `stringCount` editable base strings in the centre + `ghostStringsPerSide` (default 4) **read-only octave-repeat ghost** strings each side (global index `g` → base string `g mod stringCount`, octave `floor(g/stringCount)`), continuing the ascending svara sequence into adjacent octaves; ghosts are faint/non-editable and play the octave-shifted pitch. Default = **7 base strings, one per svara**, natural in the bottom half + komal/tivra variant in the top half: S · R/r · G/g · m/M · P · D/d · N/n (the 12 chromatic degrees). A **Perform** toggle (reuses `engine.performanceMode`) switches modes: **edit mode** — editing always on, no modifier (drag a note body = move → snap to nearest base column via `nearestBaseString`, drag its edge = resize, drag empty space = play, shift-click empty = add, right-click = delete, base notes only); **perform mode** — editing off, vertical gridlines + note labels hidden, ghosts styled identically to base (clean playing surface). The editor groups **by `stringIndex`** (one card per base string, even empty), moves a note between strings by dragging its grip handle onto another card (`.onDrop` reassigns `stringIndex`), and adds/deletes strings + notes. Toolbar **Octave ±** stepper sets `ghostStringsPerSide`. **The resolver is the generic `polyPitchAt`** (`StringPadGeometry.swift`) — **continuous EVERYWHERE, no discontinuities/dead zones** (this was a deliberate fix — an earlier `max(0, margin+sd)` clamp snapped to the nearest polygon in wide gaps, a hard switch at the midpoint). Now: **inside** a polygon → exactly its pitch (flat fixed zone); **anywhere outside** → **inverse-distance weighting** `w_s = 1/d_s^power` (normalised, log-blend) by distance to each polygon — nearer dominate, influence falls off smoothly and never cuts off, so empty space interpolates continuously (as `d_s→0`, `w_s→∞` → that polygon's pitch, matching the inside value → continuous at every boundary). A note is a **single hexagon** (rectangular middle + a **fixed-length** tip top/bottom, `stringTipLength`); the resolver uses the **whole hexagon** (NOT just the rectangle — pitch is constant across the entire hexagon, tips included), so **resizing a note's height resizes the fixed zone** — a centre-point soft-Voronoi (`pitchAt`/`chordPitchAt`) can't. Blends in **2D** (across strings too). Layout-agnostic (works for any polygons). The toolbar **Sharpness** slider repurposes `engine.marginPixels` (0–64 → `power` 1–8: higher = sharper/more Voronoi-like, lower = more global). Tonic read from `pitchPad` (kept in step by the same `start()` sink as `chordPad`). Persisted (debounced autosave to `_Current.json` via `StringArrangementStore`, ids minted on decode like `ScaleStore`). **Runs on the iPad too** (like Pitch/Chord Pad): selecting the Mac tab sets `ipadLayout = .stringPad` (a **third `PadLayout` case**), and — because the note layout is its OWN state (not derivable from the scale) — the arrangement is pushed as a **second SysEx message** (`F0 7D 02 …`, `StringArrangementSysEx`, subtype `0x02`) alongside the scale message whenever it changes while String Pad is active; `ScaleSyncReceiver` decodes it into `@Published stringArrangement` (persisted via `StringArrangementSyncStore`), and the iPad shows `StringPadViewIOS` (`PitchPadView_iOS.swift`, **always perform mode** — clean: no gridlines/labels, ghosts identical to the main octave; reuses `stringPlacements`/`polyPitchAt`/`stringFillCells`). **No** sym-pool coupling (both read only `pitchPad`). Reuses `pitchColor`/`Path(closedPolygon:)`/`SoundingState`/`CellFillsView` (each note wrapped as a `VoronoiCell` by `stringFillCells`). The current ⌘ tab order (the **FX tab** inserted at ⌘4 shifted the rest): Live ⌘1, Sarangi ⌘2, Tarab ⌘3, FX ⌘4, Simulator ⌘5, Pitch Pad ⌘6, Chord Pad ⌘7, String Pad ⌘8, Tanpura ⌘9, Sitar (no shortcut), Setup (no shortcut — ⌘ stops at 9). See [docs/string-pad.md](docs/string-pad.md).
- **Tarab tab (Mac-only, ⌘3).** The sarangi's sympathetic strings, split out of the Sarangi tab into their own grouped editor (`StarpadMac/Views/TarabView.swift`). Strings are tagged by `StringGroup` (chromatic / scale-tuned / low octave / upper octave — the 4 choirs `RagaTuning.buildChoirs` constructs) and shown one section per choir (per-choir enable-all + add). **By default the bank auto-tunes to the Pitch Pad scale**: an `AppController` sink on `pitchPad.$scale`/`$tonicMidi` (debounced) calls `syncTarabFromScale` → `SarangiStore.syncTarabToScale` → `InstrumentState.regenerateFromScale(tonicHz:ratios:)`, which rebuilds the choirs from the tonic Hz + the scale's degree ratios (`scaleDegrees(from:).map(\.ratio)`). The chromatic choir stays the fixed 15 JI ratios; the scale/low/upper choirs follow the degrees. A hand edit, choir toggle, raga pick, or tonic-set flips `autoSyncToScale` off (manual mode, edits stick); the tab's **"Follow the Pitch Pad scale"** switch / **"Re-sync"** button re-engages it (`AppController.setTarabAutoSync`). `RagaTuning.buildStrings(intervals:) -> [ResolvedString]` is unchanged (golden parity); the editable, group-tagged builder is `buildGroupedSpecs(...)`/`buildChoirs(...)`. This **reverses** the prior "tarab independent of the scale" design (user re-requested scale-sync). See [docs/sarangi.md](docs/sarangi.md).
- **FX tab (Mac-only, ⌘4).** The sarangi's **per-voice FX rack** (`StarpadMac/Views/FXView.swift`), replacing the model's old single block-F reverb. `SarangiEngine.renderSample` now splits its output into the **Violin** voice (dry + jawari, own `bodyViolin` ring) and the **Sym** voice (bank, own `bodySym` ring), applies a per-voice **FX stage** to each, sums them, then applies a **Global** stage (mid/side, so Global-off is exact passthrough). Each stage (`VoiceFX` DSP in `SarangiKit/DSP/VoiceFX.swift`, reusing `Biquad`/`BiquadChain`/`Reverb`; params `EQBand`/`VoiceFXParams`/`FXRack` in `Model/VoiceFXParams.swift`) = low-pass (cutoff+resonance) → 3-band parametric EQ → reverb (mix+width). Three sections (Violin / Sympathetic / Global), each: enable toggle, reverb (mix+width), filter, 3-band EQ; the **Violin** section also hosts **Drive (SWAM→model)** (`sarangiDriveGain`), moved here from the old Master-FX section. **Defaults: Violin FX ON** (reverb ~0.25 + open filter), **Sympathetic OFF** (dry), **Global OFF** — this intentionally drops the Sarangi-Live reverb match (the default sound changes: violin-only reverb, dry sym). The rack lives on `InstrumentState.fx` (persisted; tolerant decode; `SarangiStore.persistKey` v4). **Live vs structural:** enable + reverb mix/width are live (`AudioEngine.applySarangiFXScalars` ← `SarangiStore.applyFXChange(structural:false)`); filter/EQ/rt60 rebuild the engine (`SarangiStore` → `rebuildSarangi`); both `rebuildSarangi`/`applySarangiScalars` now take `fx: FXRack`. Audition `voiceParam` paths: `sarangi.fx.<violin|sym|global>.<enabled|reverbMix|reverbWidth|reverbRT60|filterCutoff|filterResonance>` and `sarangi.fx.<stage>.eq<0..2>.<freq|gainDB|q>` (parsed in `SarangiStore.setAuditionParam`/`setFXAudition`). See [docs/sarangi.md](docs/sarangi.md).
- **Sitar tab (Mac-only, no ⌘ shortcut).** A plucked sitar voice that **reuses `TanpuraModel` unmodified** (do NOT fork the model) with a different matched parameter set, `TanpuraParams.sitar` (in `Packages/StarpadDSP/.../SitarParams.swift`, JSON-embedded, baked by `tools/sitar_bake_defaults.py`). `AudioEngine` owns a **second** `TanpuraModel` (`sitar`) on its own source node behind `sitarLock` — identical wiring to the drone (`sitarSource → sitarGain → preReverbMixer`), API `setSitarParams`/`sitarParams`/`sitarPluck`/`clearSitarState`/`setSitarGainDB`. `AppController` holds `@Published var sitarParams` (persisted, keyed on `sitarMatchedVersion`), `sitarGainDB`, `sitarVelocity`; audition `voiceParam` paths `sitar.<path>`. Fitted to `sitar1.wav` (three C#4/280.4 Hz plucks — **all treated as the same note**) by `tools/sitar_match.py` + `tools/sitar_iterate.py` (reuse tanpura_match's specres/tune machinery + tanpura_iterate's CMA-ES; specres grid refocused to **200 Hz–13 kHz** so the reference's unmodelable low drone/sympathetic doesn't steer the fit; fit-init calibrates per-harmonic `gainTrimDB`/`decayTrim`; CMA-ES adds gtrim/dtrim group dims). The fit is **one pitch-invariant string timbre** (mirrored onto all 4 strings at 280.4 Hz). (The sarangi is now its own `SarangiKit` model, unrelated to the sitar — see [docs/sarangi.md](docs/sarangi.md).) See [docs/sitar.md](docs/sitar.md).
- **Autonomous audition**. `AuditionRunner` (Mac, started in `AppController.start()`) watches `<repo>/auditions/inbox/` for `*.json` score files; full details in [docs/simulator.md](docs/simulator.md). Event kinds: `noteOn` / `noteOff` / `glide` / `tilt` / `slider` / `strike` / `voiceParam` / `preset` / `tanpuraPluck` (tanpura model params ride `voiceParam` as `tanpura.<path>`). `voiceParam` events route through `AppController.setVoiceParam(name:value:)` and reach the same `@Published` properties the on-screen sliders set, so scripted parameter sweeps produce the same audio as if a human were dragging the UI. Output WAVs land in `<repo>/auditions/outputs/`; a sibling `.done` marker JSON (or `.error`) appears when each render finishes. **Writers must use atomic writes** (`*.json.tmp` → `mv`) — the runner waits for size-stable files but a non-atomic writer can still occasionally race. Python tools (`tools/audition_iterate.py`) already do this; bash heredocs do NOT.
- **Mac MIDI in path**. `MIDIInput` forwards every MPE channel-voice byte verbatim to the hosted AU's `scheduleMIDIEventBlock` (CC123 / RPN bend-range handling included). There is no local "modal" or "subtractive" path anymore — every Note On, CC, and Pitch Bend lands at SWAM.
- **Mac audio graph**. `N × SWAM AU(dry) → hostedDriveTap` (sums the poly instances, full level) `→ SarangiProcessorAU → symGain → mainMixerNode → output`. The sarangi model is rendered **inline** by a custom in-process AUv3 effect, `SarangiProcessorAU` (`Packages/StarpadCore/.../SarangiProcessorAU.swift`), spliced directly into the graph: its `internalRenderBlock` pulls the summed SWAM stereo synchronously into a private scratch buffer, then runs the installed `processBlock` closure (`AudioEngine.makeSarangiProcessBlock()`) — builds mono `0.5·(L+R)` lifted by `sarangiDriveGain`, runs the per-sample causal `SignalAmpFollower` for `amp`, and calls `SarangiEngine.renderSample(input, amp:)` — all under one `AudioEngine.lock` acquisition. Because it renders in the **same engine pull** as SWAM it adds **~0 ms latency** (verified `sarangiEffect_latency = 0.00 ms`; the old `installTap(4096)`→`SPSCAudioRing`→`sourceNode` transport added ~140 ms and is **deleted** — the `SPSCAudioRing` type/file, `hostedDriveRing`, `installHostedTap()`, `hostedTapInstalled`, and the muted dry branch are all gone). The effect is created **synchronously before `engine.start()`** via `AVAudioUnitEffect` after a one-time `registerSarangiAUOnce()` (component type `kAudioUnitType_Effect`, subtype `'Srng'`, manufacturer `'Strp'`) — a custom AU connected into an already-running engine does NOT allocate its render resources. The model applies its **per-voice FX rack** internally (Violin/Sym stages → sum → Global stage; no more block-F reverb) and goes `symGain → mainMixerNode` **directly, bypassing Starpad's master FX**. The master chain (`preReverbMixer → masterFilter → reverb (AVAudioUnitReverb) → postReverbEQ → mainMixerNode`) is now the room for the **tanpura + sitar only** (`tanpuraSource`/`sitarSource` → gains → `preReverbMixer`, own locks). The 4 nodes `hostedInstrumentGain`/`hostedMakeupGain`/`sarangiMixer`/`violaBodyEQ` remain **attached-but-disconnected** (so the `setViolaBodyEnabled`/`setViolaBodyBand`/`setHostedMakeupGainDB` setters stay valid); `preReverbMixer.outputVolume = 1.0` is now set once in `setupAudio`. The model also keeps its own **body** (block E, split `bodyViolin`+`bodySym`). On macOS the output IO buffer is requested down to `Config.preferredOutputBufferFrames` (128 frames ≈ 2.9 ms) at start via `AudioEngine.setOutputBufferFrames(_:)` (sets the device's CoreAudio HAL buffer, clamped — no AVAudioSession on Mac). The engine + all fitted models run at `Config.sampleRate` (44100); to avoid an output resampler, `matchOutputDeviceToEngineRate` sets the **output device's** nominal rate to 44.1 kHz at start (and on `setOutputDevice`) when the device supports it, remembering the prior rate — `restoreOutputDeviceRate` (wired to `AppController`'s `willTerminate` + `AudioEngine.deinit`) restores it on quit; a device lacking 44.1 kHz keeps AVAudioEngine's converter (best-effort). Do NOT change `Config.sampleRate` to 48000 — the body FIR is a 44.1 kHz-measured impulse response and would mistune ~+8.8%. `rebuildSarangi` swaps the `SarangiEngine` under `lock` on a structural change; `applySarangiScalars` mutates `.scalars` live; both also take `fx: FXRack`, and `applySarangiFXScalars` pushes the live FX bits (enable + reverb mix/width).
- **Presets live in `StarpadMac/SoundPreset.swift`** with a `State` struct that bundles the master FX + the **hosted-AU** setup (SWAM Violin descriptor + the **dry-SWAM `hostedAUParams`** that the model requires as input). It does **not** carry the sarangi model — that's owned by `SarangiStore`/`InstrumentState` (with its own `Presets` pair1/pair2). `AppController.applyPreset` copies FX state into `@Published` mirrors and loads the hosted AU. The shipping preset is `.swamViola` (hosts `Svl3`); the enum and picker stay in place so new hosted-AU presets can be added without re-plumbing.
- **`MappableParameter`** (in StarpadCore) is iPad-only and currently covers velocity, glide, vibrato, drag smoothing, aftertouch, and MIDI CCs 1/11/71/73/74/75. Adding a new iPad-facing dimension-mapped param means a new case here. Mac-side knobs go on `AppController` directly — they aren't part of this enum.
- **InputDimension enum** (was `Dimension`) — renamed to avoid clashing with `Foundation.Dimension` (Measurement subclass) once both modules are visible.
- **Config.swift** (in StarpadCore) holds system-level constants. Dimension-mappable parameter ranges are in **TiltMapping.swift** (`MappableParameter.defaultRange`).
- **Scale.swift** owns 12-TET frequency / note-name helpers and the `Scale` struct. Always use `scale.frequency(for:)`, never hardcode 12-TET formulas. The **iPad playing scale is a `PitchScale`** (JI `PitchPoint` ratios on the Pitch Pad, persisted via `ScaleStore`); the **sarangi tarab is a separate editable `StringSpec` table** (in `SarangiKit`, not a `Scale`). The legacy keyboard `Scale`/`ScaleEditorView` is no longer on the iPad playing path.
- **Mono/Poly modes** — iPad-side. Controls MIDI channel allocation (mono uses channel 0 only). The Mac doesn't have a poly toggle; SWAM polyphony is the configured number of hosted instances.
- **Log-frequency space**. All pitch interpolation uses `log2(freq)` for perceptually linear movement.
- **MPE per note**. Each note activation on iPad gets a fresh MIDI channel (round-robin 1-15).
- **iPad dimension system**. Parameters are driven by configurable dimensions (tilts, pressure, key Y, sliders). Use `cachedParamValue(for:voiceIndex:)` in the hot path — never the dictionary-based lookup.
- **60Hz glide loop** (iPad) on main thread drives all continuous updates (pitch, tilt, MIDI). The played pitch tracks the finger directly via `pitchAt`; the Mac sends the bend immediately from `glide` (no loop). Note the automatic vibrato LFO has been removed — vibrato is now a playing technique (move the finger).
- **Audio thread** (Mac) runs `SarangiProcessorAU.internalRenderBlock` — it pulls the upstream SWAM input and runs the model closure (`SignalAmpFollower` + `SarangiEngine.renderSample`) under `lock`; never does MIDI or state logic.
- **SwiftUI updates are throttled** to ~15Hz via manual `objectWillChange.send()` on the iPad's `NoteManager`.

## Building

iOS:
```bash
cd Starpad
xcodebuild -project Starpad.xcodeproj -scheme Starpad \
  -destination 'platform=iOS Simulator,name=iPad Air 13-inch (M3)' \
  build 2>&1 | grep -E "error:|warning:"
```

macOS:
```bash
cd Starpad
xcodebuild -project Starpad.xcodeproj -scheme StarpadMac \
  -destination 'platform=macOS,arch=arm64' \
  build 2>&1 | grep -E "error:|warning:"
```

Or from the repo root:
```bash
./tools/build-mac.sh
```
This script wraps the macOS build, filters out non-actionable noise, and exits non-zero on errors. Wire it into a pre-commit hook or CI step so a refactor that breaks `StarpadMac` while iOS still compiles catches before merge.

DSP package tests:
```bash
cd Packages/StarpadDSP && swift test
```

The iPad simulator destination name may vary. Check available destinations with:
```bash
xcodebuild -project Starpad.xcodeproj -scheme Starpad -showdestinations 2>&1 | grep "iPad"
```

Physical device required for accelerometer, gyroscope, and MIDI output.

## Adding Files to the Xcode Project

**For files in `Packages/StarpadCore/Sources/StarpadCore/`** — drop the `.swift` file in that directory. SPM auto-discovers it; no pbxproj edit needed. Make sure types/init/methods used outside the package are `public`.

**For files in iOS target (`Starpad/Starpad/`) or macOS target (`StarpadMac/`)** — manually add to `Starpad.xcodeproj/project.pbxproj`:
1. Add a `PBXBuildFile` entry (`A1xxxxxx` for iOS, `C1xxxxxx` for macOS)
2. Add a `PBXFileReference` entry (`A2xxxxxx` / `C2xxxxxx`)
3. Add to the `PBXGroup` children list (iOS: `A5000002`, macOS: `C5000001`)
4. Add to the appropriate `PBXSourcesBuildPhase` files list (iOS: `A7000001`, macOS: `C7000001`)

Use sequential IDs following the existing pattern.

## Sound Design Iteration

The sarangi is the ported **`SarangiKit`** model (see [docs/sarangi.md](docs/sarangi.md)) — a block chain (A pre-EQ, B sympathetic Karplus-Strong bank, C jawari exciter, E body FIR + modal formants; the D drone block was removed; block F reverb is now the per-voice FX rack) that turns the **dry SWAM Violin** into the complete sarangi. It was fitted **offline in the separate `~/Desktop/sarangi` project** (its own `run.py`/`fit.py`/`sarangi-render` + CMA-ES against `target1/2.wav`); Starpad **vendors the fitted DSP package** and does not re-fit. To change the sound from inside Starpad:

- **Edit live in the Sarangi tab (⌘2)** (`SarangiEditorView`): presets + the **grouped param sliders** (Bank/Jawari/Body/Mix; the Reverb group is empty — F_* removed). A change routes through `SarangiStore.setParam` → either a **live-scalar** push (`AudioEngine.applySarangiScalars`) or a **debounced structural rebuild** (`AudioEngine.rebuildSarangi`), keyed off `ParamDescriptor.structural`. **Reverb/filter/EQ live in the FX tab (⌘4)** (`FXView`) — the per-voice FX rack (Violin/Sym/Global; Drive also lives there). The **sympathetic strings + tuning live in the Tarab tab (⌘3)** (`TarabView`) — auto-synced to the Pitch Pad scale by default.
- **LEVELS (load-bearing — the model is under-driven in-app):** raw in-app SWAM is ~50× quieter than the fit reference (`input1.wav`, RMS 0.30), so the model — esp. the excitation-driven sym — is far too quiet. Three Starpad knobs: **"Drive (SWAM→model)"** (`AudioEngine.sarangiDriveGain`, def 10, lifts SWAM before the amp follower + model — trim to playing dynamics), **`sym_gain`** (the **bank** is intrinsically ~30 dB below the main, so range 0–40, def **12** ≈ audible halo), **`main_gain`** (def 1.0). A **soft limiter** (`SarangiEngine.softClip`, <0.9 linear) backstops loud peaks. `main_gain`/`sym_gain` apply at the output MIX only, so `main_gain` never changes the sym EXCITATION (the bank is driven by the raw drive before the gains). Diagnose with `DriveLevelTests`/`OnsetLagTests` (`swift test --filter DriveLevel`).
- **Params** (`Packages/SarangiKit/.../Model/ParamSpec.swift`): brightness/buzz via the **Jawari** group (`C_drive_max`, `C_wet`, `C_top`, `C_sweep_hi`); sympathetic level via **Bank** (`B_gain`, `B_bright`) + `mix_bank` + `sym_gain`; body via **Body** (`E_body`, `E_low_shelf_*`); balance via the **Mix** group (`mix_dry/bank/jaw`, `main_gain`/`sym_gain`) + `gin`/`gout`.
- **Presets**: `Presets.state(.pair1/.pair2)` (E♭ harm-minor / Bhairav) load a full `InstrumentState` (strings + params + 1025-tap body FIR). With tarab auto-sync ON (default), the loaded strings are immediately re-tuned to the Pitch Pad scale (loadPreset preserves the sync flag; the toolbar calls `syncTarabFromScale`); the preset still supplies the timbre (params + FIR). Turn off auto-sync (Tarab tab) to keep a preset's exact strings.
- **Persistence**: `SarangiStore` auto-saves the `InstrumentState` to UserDefaults; export/import as `.sarangi` JSON. To make a change the shipping default, save it into the upstream `pairN.json` (re-fit in `~/Desktop/sarangi`) and recopy the resources.
- **Master FX** — the AVAudioUnit master FX (`reverbMix`/`filterCutoff`/`filterResonance` + `violaBody*`/`postReverb*`) is now the tanpura/sitar **Room** (relocated to the Tanpura tab as the "Room (tanpura + sitar)" section); the sarangi bypasses it and uses its own **per-voice FX rack** (FX tab, ⌘4) + body (block E).

To re-fit the model or change its DSP, work in `~/Desktop/sarangi`, then re-vendor `Packages/SarangiKit/Sources/SarangiKit/{DSP,Model}` + `Resources/*.json`. Don't fork the DSP into Starpad.
