## Key Conventions

- **Two devices, one cable, almost no shared state**. iPad is a MIDI controller (USB-MIDI only — no Bonjour/Wi-Fi). It owns its glide/vibrato params, calibration, and the MPE emission. Mac is the **sarangi model** (`SarangiKit`: the fitted source + chain — the default base voice is our own fitted `ViolinSynth`; a dry-run hosted **SWAM** AU or the sitar model are the alternatives) + tanpura/sitar + FX layer. It owns the sarangi model state, master FX, presets, and hosted-AU selection. The two communicate only over the USB cable. **Do not introduce shared params** beyond the one documented exception below — if a feature wants to live on one side, all its state lives on that side.
- **The one exception: pad sync (Mac → iPad over SysEx).** StarpadMac edits; Starpad performs. The Mac pushes a `SyncedScaleState` (the `PitchScale` **plus `tonicMidi`, `marginPixels`, and the active `layout`** — `PadLayout.pitchPad`/`.chordPad`/`.stringPad`/`.fretPad`, which surface the iPad shows; `marginPixels` is the **active** layout's margin/sharpness/snap, since each pad owns its own slider) to the iPad as a MIDI **SysEx** blob on the same USB cable: `PitchScaleSysEx.encode` = `F0 7D 01 base64(compact-binary) F7` (kept small so it clears the iOS USB-MIDI SysEx bridge; blob `version` is now `3`). The iPad's `ScaleSyncReceiver` receives it via an **input port connected to every source** (USB-incoming MIDI arrives as a *source* on the iPad — a virtual destination does NOT catch it; this was the bug) plus a virtual destination as backup, reassembles SysEx across packets/callbacks, and calls `PitchPadEngine.applySyncedState` (panics on scale **or layout** change, swaps scale/tonic/margin/layout). It persists to `SyncedScaleStore` (UserDefaults) for offline relaunch. One-way; the iPad has **no** scale editor, its tonic readout is read-only, and it can't pick its own layout. Push is driven from `AppController` via Combine: `Publishers.MergeMany` of `pitchPad.$scale` / `$tonicMidi` / `$marginPixels` / `chordPad.$marginPixels` / `stringPad.$marginPixels` / `fretPad.$marginPixels` / `$stringArrangement` / `$fretArrangement` / `$ipadLayout` / `midi.$destinationCount`, debounced, → `MIDIEngine.sendSysEx(_:toDestinationsMatching: "Starpad")` (falls back to all destinations if the name matches none — the bridged iPad endpoint shows up as "iPad", not "Starpad Scale"). **Second SysEx message:** the String Pad's note layout is its own state (not derivable from the scale), so while `.stringPad` is active the Mac ALSO pushes `StringArrangementSysEx.encode` = `F0 7D 02 base64(…) F7` (subtype `0x02`); `ScaleSyncReceiver` decodes it into its `@Published stringArrangement` (persisted via `StringArrangementSyncStore`). **Third SysEx message:** likewise the Fret Pad's segment layout — while `.fretPad` is active the Mac pushes `FretArrangementSysEx.encode` = `F0 7D 03 base64(…) F7` (subtype `0x03`) into `@Published fretArrangement` (persisted via `FretArrangementSyncStore`). These three messages are the **only** SysEx and the **only** cross-device state in the app.
- **StarpadCore package** (`Packages/StarpadCore/`) — cross-platform building blocks: `Scale`, `MIDIEngine`, `MIDIInput`, `Config`, `MotionSource` protocol, `CalibrationData`. Also includes the **shared Pitch Pad** (`PitchPadEngine` — per-touch MPE + iPad tilt loop; `PitchPadGeometry.swift` — Voronoi solver/caches, soft-margin `pitchAt`, octave ghosts, OKLCH colors, `CellFillsView`; `ChordPadGeometry.swift` — the shared **Chord Pad** geometry (hex lattice, `chordCells` diatonic-chord pitch model, `chordPitchAt` soft-margin blend, hex polygons; reuses `pitchColor`/`CellFillsView`); `ScaleStore` — JSON scale persistence; `PitchPoint`/`PitchScale`), `NoteManager` (tilt/mapping host), and `AudioEngine` + `SarangiProcessorAU` (Mac-only audio — the in-process AUv3 effect that renders the sarangi model inline in the SWAM signal path). `PitchPadEngine` has two inits: `init(audio:)` (Mac, in-process delivery to `AudioEngine`) and `init(midi:)` (iPad, real USB-MPE through the shared `MIDIEngine`). Both iOS and macOS targets import the same package; each only uses the parts that apply. **Anything used outside the package must be `public`.**
- **SarangiKit package** (`Packages/SarangiKit/`) — the **played sarangi voice**, vendored wholesale from the standalone `~/Desktop/sarangi` model (pure DSP + model, no CoreAudio; re-sync by recopying `Sources/SarangiKit/{DSP,Model,Violin,Bow}` + `Sources/CBowKernel` + the resources; Starpad-local divergences: `VoiceEQBand` rename (upstream calls it `EQBand` — clashes with the FX rack's), `StringGroup` `groups`+`freqs` threading through `ResonatorBank.build`, `CombString.period`/`bufferCopy()`, the FX-rack files, the MARKED "Starpad" sections in `SarangiEngine` (2-stage FX, spectrum rings, `bankRawSnapshot`), and the **MPE sections in `Bow/BowControls.swift`** (per-channel bend `chBend`, slot `ch`, CC75 tilt)). TWO instruments: (1) **the String voice** — `Bow/` (`BowEngine`/`BowTables`/`BowControls`/`BowConfig`/`BowFpMask`/`HalfBandDecimator`) + the **`CBowKernel` C target** (`bow_kernel.c` mono + `bow_kernel_poly.c` poly, `cSettings: -O3` ALWAYS — the offline reference dylib is `cc -O3` and a debug kernel runs far below realtime), fed by `bowed_string.json`; (2) **the coupled network** — `SarangiEngine.renderSample(input) -> (L,R)` after `beginBuffer()` (drive in → complete stereo sarangi out; **silent unless armed** by a passive `CoupledConfig`) — the SWAM/sitar chain. `Violin/` is the v57 SOURCE kept for parity tests (`ViolinModel`/`ViolinSynth`/`ExprEqualizer` + `sarangi_model_v57.json`, 48 kHz; no longer a Starpad base voice). Model types: `SarangiParams` (**25** params via `ParamSpec`, `structural` flag; incl. `N_jaw_*` per-class jawari), `LiveScalars` (+ Starpad `applyFX`), `VoiceEQBand`, `EQBand`/`VoiceFXParams`/`FXRack`, `RagaTuning`/`Raga`/`StringSpec` (editable tarab + `raga` class flag), `CoupledConfig`/`BodyAdmittance`/`WModalBank`, `BowParams`/`BowTuning`/`BowKernelTables` (the String artifact schema), `InstrumentState`, `Presets` (ONE preset **sarangi_pilu** + `sarangi_pilu_strings.json` exact table + `sarangi_coupled.json` + `sarangi_model_v57.json` + `live_comp.json` + **`bowed_string.json`**). `StarpadCore.AudioEngine` imports it (`StringVoiceSource` node for the String voice; the `SarangiProcessorAU` effect runs `renderSample` inline for SWAM/sitar). See [docs/sarangi.md](docs/sarangi.md). **`StarpadDSP` no longer owns any sym/sarangi DSP** — it was all deleted (`OfflineEngine`, `SarangiResonator`, `SarangiSymVoice`, `SarangiExciter`, `SymBodyFilter`, `SchroederRoom`, `DSPParams`, `DSPConfig`, the `sym-render` tool).
- **StarpadDSP package** (`Packages/StarpadDSP/`) owns the **tanpura drone + sitar** (only — the sarangi moved to `SarangiKit`): the **tanpura** (`TanpuraModel`/`TanpuraString`/`TanpuraParams`): 4 harmonic-resolved strings where every harmonic (up to 64) gets its own bloom envelope (gain/peak-time/decay laws + per-harmonic trim arrays) plus a per-string **half-integer sub-bank** (`subLevelDB`, partials at `(k+0.5)·f0` — the jawari period-2 signature, loud in the reference), matched to `tanpura.mp3` by `tools/tanpura_match.py` + `tools/tanpura_iterate.py` through the package's **`tanpura-render` executable** (offline, ~50× real time; build with `swift build -c release --package-path Packages/StarpadDSP`). The primary metric is `specres` (per-cell |ΔdB|, absolute 90 Hz–16 kHz grids) judged against the two-seed stochastic floor; `tanpura_match.py report <wav> --floor <wav2> --diff-audio` is the acceptance-bar artifact. The match generalizes across **8 reference recordings** — `tanpura.mp3` (densely strummed, has the per-harmonic matrices) plus `tanpura1–7.wav` (varied tonics/density; calibrated by `calibrate-aux` into `auditions/tanpura/refs/<name>/`, scored by an aux minibatch with per-reference tuning and shared timbre). The isolated-pluck "wah-wah" (the summed envelope pumps) is fixed by `jivaConserve` (power-conserving jiva) + `jivaRateSpread` (tightens the per-harmonic rate scatter) under the `modspec` loss term (penalizes envelope-modulation energy above the reference's tight ~2 Hz pulse). Matched winners are baked into the `TanpuraParams` Swift defaults by `tools/tanpura_bake_defaults.py --bump` (peak-normalizes `masterGain`, bumps `matchedVersion` so persisted UserDefaults don't shadow the new bake). **Before trusting any matching run, verify the pluck schedule with `tanpura_match.py schedule-check`** — the loss conditions on it. `StarpadCore.AudioEngine` imports the package — the tanpura on its own source node behind `tanpuraLock`, the sitar likewise behind `sitarLock` (the **sarangi** runs the full model — incl. its 2-stage FX rack (violinPre/Global) — inline in the `SarangiProcessorAU` effect (spliced after the SWAM AUs) from `SarangiKit`, going `symGain → mainMixerNode` direct, BYPASSING the master FX; only tanpura/sitar use `preReverbMixer`→master reverb); don't duplicate DSP logic in any consumer. See [docs/tanpura.md](docs/tanpura.md) and [docs/sitar.md](docs/sitar.md).
- **iPad playing surface: the Pitch Pad** (`PitchPadEngine` + `PitchPadView_iOS.swift`), shared with the Mac Pitch Pad tab. It replaced the piano keyboard. Touch position → JI ratio (shared `pitchAt` soft-Voronoi in `PitchPadGeometry.swift`) → `PitchPadEngine` pins a MIDI note and bends; a 60 Hz tilt loop (started in the iPad `init(midi:)`) overlays vibrato/aftertouch/CC. The pad is multitouch-polyphonic (one MPE channel per finger) and play-only on iPad (editing via the list-editor sheet); the Mac tab has the full editing toolkit. The iPad does not synthesize; it only emits MIDI.
- **`NoteManager` (iPad) is now the tilt/mapping host, not the playing orchestrator.** It still runs (its 60 Hz loop samples tilt into `currentTilt` and owns the `DimensionMapping` matrix that `MappingMatrixPanel` edits), and `PitchPadEngine.expression` is a weak ref to it for `cachedParamValue(...)` / `activeCCs`. Its keyboard/glide/voice (`pitchChannels`) MIDI paths stay idle because nothing calls its `touchBegan`. The old keyboard/glide-queue/snap pipeline lives on but is unused on the playing path.
- **Mac orchestration: `AppController`**. Owns the editable Mac state (the `SarangiStore` for the sarangi model, tanpura/sitar params, master FX, current preset). On preset switch or slider change, it pushes directly to `AudioEngine`. `NoteManager` is **not used** on the Mac for real-iPad MIDI input — but the **Simulator tab** (`StarpadMac/IPadSimulator.swift`) owns its own `NoteManager` + `MockMotionSource` so the Mac can play notes from a mouse + tilt sliders, for autonomous sound-design iteration. The simulator's `MIDIEngine` uses `publishToCoreMIDI: false` and an in-process `onLocalEvent` callback to deliver MIDI directly into `AudioEngine.sendHostedMIDI` + `AppController.handleSimulatorCC`, so it never feeds `MIDIInput` and coexists with a plugged-in iPad.
- **Chord Pad tab (Mac-only).** `AppController` holds a **second** `PitchPadEngine` (`chordPad`, beside `pitchPad`, also `init(audio:)`/in-process) as the MPE emitter for the hex-grid chord surface (`StarpadMac/Views/ChordPadView.swift`). The grid (`ChordPadGeometry.swift`) maps a diatonic scale → per-cell `2^(semis/12)` ratios and feeds the engine's ratio API; it **reads** the scale + tonic from `pitchPad` (read-only — `chordPad.tonicMidi` is kept in step via a Combine sink in `start()`), adds **no** cross-device state, and is not part of scale sync. The two Mac engines round-robin the same 15 MPE channels, so play one pad at a time. Common scales are **shared**, not Chord-Pad-local: `ScalePreset` (modes, major/minor, pentatonics, in `ChordPadGeometry.swift`) loads into the one `pitchPad.scale` via `PitchPadEngine.loadPreset`, reachable from both the Chord Pad toolbar and the Pitch Pad's Scale → Scales submenu. The Chord Pad **also runs on the iPad** (`ChordPadViewIOS` in `PitchPadView_iOS.swift`): selecting the Mac's **Pitch Pad** or **Chord Pad** tab sets `AppController.ipadLayout` (via `MacMainWindow.selectTab`, covering both the segmented picker and the ⌘-number shortcuts), which rides the synced state, and the iPad swaps surfaces on `pad.layout`. See [docs/chord-pad.md](docs/chord-pad.md).
- **String Pad tab (Mac-only, ⌘9).** A box-plot / abacus surface (`StarpadMac/Views/StringPadView.swift`). `AppController` holds a **third** `PitchPadEngine` (`stringPad`, beside `pitchPad`/`chordPad`, `init(audio:)`/in-process) as the MPE emitter, plus `@Published var stringArrangement` (a `StringArrangement` = `notes:[StringNote]` + `stringCount` + `ghostStringsPerSide` + `rotationDegrees` — iPad-only tilt, see the iPad note below). **Strings are explicit, evenly-spaced indexed columns** — a `StringNote` has `stringIndex` (NOT a free `x`), `degreeIndex`, `octave`, `centerY`, `height`. A **note** = name + pitch + `centerY` + `height`, drawn as a **single hexagon** (rectangular middle + a fixed-length tip top/bottom, `stringTipLength`) with **constant pitch throughout** (tips included). A note's pitch is a **scale degree** of `pitchPad.scale` (+ octave), looked up live (`scaleDegrees(from:)`/`noteRatio`), and its **name is sargam** derived from the pitch (`noteName`/`sargamName`: S r R g G m M P d D n N = degrees 1, 2♭, 2, 3♭, 3, 4, 4♯, 5, 6♭, 6, 7♭, 7 of the default scale; `'`/`,` = octave up/down). **Strings repeat across octaves**: `stringColumns()` lays out `stringCount` editable base strings in the centre + `ghostStringsPerSide` (default 4) **read-only octave-repeat ghost** strings each side (global index `g` → base string `g mod stringCount`, octave `floor(g/stringCount)`), continuing the ascending svara sequence into adjacent octaves; ghosts are faint/non-editable and play the octave-shifted pitch. Default = **7 base strings, one per svara**, natural in the bottom half + komal/tivra variant in the top half: S · R/r · G/g · m/M · P · D/d · N/n (the 12 chromatic degrees). A **Perform** toggle (reuses `engine.performanceMode`) switches modes: **edit mode** — editing always on, no modifier (drag a note body = move → snap to nearest base column via `nearestBaseString`, drag its edge = resize, drag empty space = play, shift-click empty = add, right-click = delete, base notes only); **perform mode** — editing off, vertical gridlines + note labels hidden, ghosts styled identically to base (clean playing surface). The editor groups **by `stringIndex`** (one card per base string, even empty), moves a note between strings by dragging its grip handle onto another card (`.onDrop` reassigns `stringIndex`), and adds/deletes strings + notes. Toolbar **Octave ±** stepper sets `ghostStringsPerSide`. **The resolver is the generic `polyPitchAt`** (`StringPadGeometry.swift`) — **continuous EVERYWHERE, no discontinuities/dead zones** (this was a deliberate fix — an earlier `max(0, margin+sd)` clamp snapped to the nearest polygon in wide gaps, a hard switch at the midpoint). Now: **inside** a polygon → exactly its pitch (flat fixed zone); **anywhere outside** → **inverse-distance weighting** `w_s = 1/d_s^power` (normalised, log-blend) by distance to each polygon — nearer dominate, influence falls off smoothly and never cuts off, so empty space interpolates continuously (as `d_s→0`, `w_s→∞` → that polygon's pitch, matching the inside value → continuous at every boundary). A note is a **single hexagon** (rectangular middle + a **fixed-length** tip top/bottom, `stringTipLength`); the resolver uses the **whole hexagon** (NOT just the rectangle — pitch is constant across the entire hexagon, tips included), so **resizing a note's height resizes the fixed zone** — a centre-point soft-Voronoi (`pitchAt`/`chordPitchAt`) can't. Blends in **2D** (across strings too). Layout-agnostic (works for any polygons). The toolbar **Sharpness** slider repurposes `engine.marginPixels` (0–64 → `power` 1–8: higher = sharper/more Voronoi-like, lower = more global). Tonic read from `pitchPad` (kept in step by the same `start()` sink as `chordPad`). Persisted (debounced autosave to `_Current.json` via `StringArrangementStore`, ids minted on decode like `ScaleStore`). **Runs on the iPad too** (like Pitch/Chord Pad): selecting the Mac tab sets `ipadLayout = .stringPad` (a **third `PadLayout` case**), and — because the note layout is its OWN state (not derivable from the scale) — the arrangement is pushed as a **second SysEx message** (`F0 7D 02 …`, `StringArrangementSysEx`, subtype `0x02`) alongside the scale message whenever it changes while String Pad is active; `ScaleSyncReceiver` decodes it into `@Published stringArrangement` (persisted via `StringArrangementSyncStore`), and the iPad shows `StringPadViewIOS` (`PitchPadView_iOS.swift`, **always perform mode** — clean: no gridlines/labels). **The iPad mirrors the Mac layout, ROTATED** by a **configurable angle `rotationDegrees` (0–40°, default 30°)** set on the Mac toolbar's **Rotation** slider (iPad-only; the Mac surface stays upright). `StringPadSurfaceIOS.diagonalFillCells` calls the SAME shared `stringPlacements` (so note heights/band/ghosts correspond to the Mac — NOT stretched) then rotates each hexagon polygon about the box centre onto the screen centre, **directly in screen space** (no `rotationEffect`, so `polyPitchAt` resolves touches in the same space — no inverse transform, no nested-UIView hit-test concern). It keeps the Mac column density + adds octave-repeat ghosts to span the rotated width, box height = screen height (Mac-sized hexagons). `rotationDegrees` rides the same `StringArrangementSysEx` (blob version 2) + `StringArrangementStore` (doc version 3). **No** sym-pool coupling (both read only `pitchPad`). Reuses `pitchColor`/`Path(closedPolygon:)`/`SoundingState`/`CellFillsView` (each note wrapped as a `VoronoiCell` by `stringFillCells`). Drags NEVER re-snap discretely: pitch = `2^(rawLog(x) + snapOffsetLog + assistCorrection)` where `snapOffsetLog` is the constant log2 delta captured at a snapped onset (exact at onset, meend/vibrato relative to it, cleared on note-off) and `assistCorrection` is the **drag assist** (`FretDragAssist`, StarpadCore, 2026-07-16, **constants FITTED to real iPad playing** — see fit provenance in docs/fret-pad.md): a gated magnetic correction — slewed toward the nearest fret at rate = gate × proximity × settle, where gate = min(1, max(stationarity(smoothed |dx/dt|, 1 below 59 px/s → 0 above 375, τ 26 ms), **turnGain 2.0 × direction-flip impulse** (deadbanded dx sign change fires impulse=1 decaying with turnTau 26 ms — fast connected turns (~30 ms) are invisible to any speed average; the flip is causal with ~1-event latency))), proximity = within the **assist basin = radiusScale 1.75 × Snap ≈ 75¢ at the 24 px default** in log-pitch (fast landings are ~2× sloppier than the onset radius; onset snap stays 1×) AND the fret's y-extent (full pull inside half the basin → 0 at the edge), settle τ 5 ms **bounded by a hard slew cap ≈ 1500 ¢/s** on the correction ⇒ smoothness by construction. Stops land exactly on the fret, fast turns get pulled onto it as the note speaks, fast transit/vibrato is untouched, and with no qualifying fret the correction FREEZES (carried tuning anchor — never decays mid-hold). Fit result on the 8×9-note phrase recording: landing error 39.7¢ → 29.3¢, transit warping ~2¢; the recording covers fast connected playing only — refit with slow glides/vibrato to regularize (high speedCeiling makes slow glides sticky near frets). Stops emit no events ⇒ a 60 Hz Timer per surface drives `tick()` → `engine.glide` while touches are down (timer closures capture only engine+assist, never the view struct; it also runs while a legato release is pending and self-invalidates when idle — iOS re-arms on `assistTimer?.isValid != true`, NOT nil-check). **Tap legato** (`FretLegato`, StarpadCore, toolbar "Legato" toggle, default ON, carried as `FretArrangement.legato` → store doc v3 / SysEx blob v3 flags byte): for very fast phrases the player TAPS notes instead of dragging — a tap while the previous note sounds (or within the ~120 ms release grace window; owner releases are DEFERRED that long) takes the voice over via `PitchPadEngine.transferTouch(from:to:)` (ownership moves with NO MIDI events — one articulation, bends only = true legato for SWAM/the model; returns false on stale state → caller falls back to fresh noteOn) and **glides** old→new pitch over ~50 ms as an additive smoothstep offset on top of the assist output (starts at exactly the old pitch ⇒ no discontinuity). ## Sound Design Iteration

The sarangi is the ported **`SarangiKit`** model (see [docs/sarangi.md](docs/sarangi.md)). The DEFAULT played voice is the **String instrument** (`BowEngine` + `CBowKernel`, driven by `bowed_string.json`; taraf tuning = the Tarab tab rows, physics/room/level = `bow_*` artifact keys, overridable via audition `string.<key>` or `AudioEngine.setStringVoiceOverrides`); the **coupled bridge–body network** (`SarangiEngine.renderSample(input)`; Sarangi-tab 25 params + 2-stage FX rack) colors the SWAM/sitar base voices. Both were fitted **offline in the separate `~/Desktop/sarangi` project**; Starpad **vendors the fitted DSP package** and does not re-fit. To change the sound from inside Starpad:

- **Edit live in the Sarangi tab (⌘3)** (`SarangiEditorView`): the preset menu + the **String physics editor** (`StringParamsView` over `StringParamStore` — 7 groups of `bowed_string.json` scalars, ported row-for-row from the upstream Sarangi Live editor; edits ride a persisted override dict `starpad.stringOverrides.v1` → `AudioEngine.setStringVoiceOverrides` → debounced off-main `BowEngine` rebuild; "Default (Sarangi Live)" clears every override, double-click a row label resets one). Below it, collapsed: the **25 coupled-network params** (Bank/Drone/Body/Reverb/Mix — SWAM/sitar chain only; `SarangiStore.setParam` → live-scalar push or debounced structural rebuild, keyed off `ParamDescriptor.structural`). **The FX rack lives in the FX tab (⌘5)** (`FXView`, both stages default OFF; Drive lives there too — network path only). The **sympathetic strings + tuning live in the Tarab tab (⌘4)** (`TarabView`) — auto-sync to the Pitch Pad scale starts OFF (String-era default; the fitted Pilu table sticks) and is opt-in via the tab's switch.
- **LEVELS:** with the **model source** (default), calibration is inside the fitted preset — `gin 2.6` lifts the synth level to the fit reference, `gout 0.45` leaves softClip headroom, `main_gain` = 1, drive = 1; the Mac pads hold flat CC11 = **32** (the fitted expr median — CC11 is a real ±16 dB loudness axis here). With a **SWAM base** trim **"Drive (source→model)"** (`AudioEngine.sarangiDriveGain`, def 1) upward. A **soft limiter** (`SarangiEngine.softClip`, <0.9 linear) backstops loud peaks. `main_gain` applies at the output only (never changes how hard the strings are driven).
- **String params** (the played voice; `StarpadMac/Views/StringParamsView.swift` groups, verbatim from upstream): **Body (formula modes)** `bow_body_*`/`bow_yinf`/`bow_kret`; **Bow & string** `bow_mu_*`/`bow_v0`/`bow_Zt`/`bow_gut_*`/`bow_nut_fc`/`bow_br_fc`/`bow_noise*`/`bow_tors_*`/`bow_age_*`/`bow_cr_*`; **Playing ranges** `bow_v_lo/hi`/`bow_live_beta_*`/`bow_live_press_*`/`bow_expr_lift`/`bow_f_cap`; **Jawari taraf** `bow_jtaraf_on`/`bow_jt_*`; **Taraf** `bow_taraf_*`/`bow_open_*`; **Articulation** `bow_place_ms`/`bow_draw_*`/`bow_attack_*`/`bow_vib_*`; **Radiation & output** `bow_rad_*`/`bow_w`/`bow_live_trim`/`bow_rev_*`. Audition path `string.<key>` (routes through the store → shows in the UI + persists).
- **Network params** (`Packages/SarangiKit/.../Model/ParamSpec.swift`, **25** — SWAM/sitar chain only): Bank (`B_*` web + `N_taraf_dir*` tap + `N_jaw_*` per-class jawari buzz), Drone (`mix_drone` + `D_*`, fitted 0), Body (`E_lp`), Reverb (`F_*`, fitted 0), Mix (`main_gain`) + `gin`/`gout`.
- **Preset**: **"Default (Sarangi Live) — Pilu, fitted"** (`SarangiStore.loadSarangiLiveDefault` + `StringParamStore.resetToDefault`) = the upstream default instrument exactly: untouched `bowed_string.json` physics, the EXACT fitted Pilu string table, Sa 328.9 Hz, auto-sync OFF. It is the ONLY preset and the fresh-install default.
- **Persistence**: `SarangiStore` auto-saves the `InstrumentState` to UserDefaults (`starpad.sarangiState.v8`); String overrides in `starpad.stringOverrides.v1`; export/import as `.sarangi` JSON. To make a change the shipping default, land it upstream in `~/Desktop/sarangi` (params/bowed_string.json / sarangi_pilu.json / sarangi_coupled.json) and re-vendor the resources.
- **Master FX** — the AVAudioUnit master FX (`reverbMix`/`filterCutoff`/`filterResonance` + `violaBody*`/`postReverb*`) is now the tanpura/sitar **Room** (relocated to the Tanpura tab as the "Room (tanpura + sitar)" section); the sarangi bypasses it and uses its own **FX rack** (FX tab, ⌘5) + body (the coupled network's modal body + radiation FIR).

To re-fit the model or change its DSP, work in `~/Desktop/sarangi`, then re-vendor `Packages/SarangiKit/Sources/SarangiKit/{DSP,Model,Violin,Bow}` + `Sources/CBowKernel` + the resources (recopy `params/bowed_string.json`, `params/sarangi_model_v57.json`, `params/sarangi_coupled.json`, `params/live_comp.json`, and `app/Sources/SarangiState/Resources/sarangi_pilu*.json`; re-apply the Starpad divergences listed under the SarangiKit package bullet — incl. the MPE sections in `Bow/BowControls.swift`). The coupled artifact carries its own 44.1 kHz radiation FIR (`N_rfir`) — no more Starpad-side FIR re-bakes. Don't fork the DSP into Starpad.
